# 반응성 최적화 실측 — 2026-09-20

## 전체 앱 후속 측정

사용자 요청에 따라 장시간 모델 추론은 실행하지 않았다. 실제 App·FontsProvider·AppSession을 배포용 React profiling 빌드로 실행하고, 저장소 QA 브리지에 격리한 30/500페이지(페이지당 20블록)와 제어된 작업 이벤트를 공급했다. GPU 가속을 끈 별도 Chromium 프로필을 사용했다. 아래 React 시간은 commit의 render duration 합계이며 사용자 입력부터 화면 표시까지의 지연 시간은 아니다.

이번에는 페이지별 활동 목록을 매번 재탐색하던 중첩 순회를 제거했다. 화 단위 잠금 집합과 선택 페이지의 입력 마무리 잠금을 따로 memoize해 페이지 이동 때 전체 잠금 집합을 다시 만들지 않는다. 블록 수·인페인팅 완료 수·인접 이미지 대상도 관련 입력이 바뀔 때만 계산한다. 자원 충돌 규칙과 모델 독점은 그대로다.

| 잠금 해석 100회, 5회 측정 중앙값 |  변경 전 | 변경 후 |
| -------------------------------- | -------: | ------: |
| 30페이지                         |   3.13ms |  1.05ms |
| 500페이지                        | 190.20ms |  6.61ms |

이는 잠금 계산 구간의 개선이며 전체 앱이 29배 빨라졌다는 뜻은 아니다. 원자료는 `.tmp/responsiveness-final/locks-before.json`, `locks-after.json`에 남겼다.

전체 앱의 수정 후 배포 빌드 측정(`production-*.json`):

| 조건                           | 30페이지                             | 500페이지                                 |
| ------------------------------ | ------------------------------------ | ----------------------------------------- |
| 페이지 이동 20회               | 57 commits / 407.5ms / long task 0회 | 65 commits / 469.2ms / 50ms long task 1회 |
| 진행 이벤트 1,020회 / 30프레임 | 89 commits / 90.4ms                  | 89 commits / 84.2ms                       |
| B 페이지 편집·자동 저장        | 2 commits / 30.6ms / 저장 1회        | 2 commits / 16.5ms / 저장 1회             |

진행 이벤트 구간은 두 크기 모두 글자 배치 재측정 0회, long task 0회였다. 최초 보관함·화 조회는 각각 1회이고 진행 이벤트가 화를 다시 열지 않았다. A의 글은 readonly 상태에서도 포커스·복사가 가능했고 B 편집 결과는 격리 저장 데이터에 반영됐다. 브리지의 저장 성공은 실제 main IPC 보호를 입증하지 않으므로, main의 자원 충돌·동일 대상·모델 직렬화는 별도 회귀 테스트를 근거로 삼는다.

수정 확인 실행(`confirmed-*.json`)에서도 같은 기능 검증을 통과했다. 500페이지 이동은 525.2ms·53ms long task 1회로 변동했다. 페이지를 바꾸면 새 페이지의 글자 배치는 여전히 필요하며 모든 이동 지연이 사라졌다고 판정하지 않았다. 기존 저장 응답 병합 성능 회귀도 30페이지 0.6ms / 500페이지 0.8ms, 원본 블록 재해싱 0회로 유지했다. 모든 저장 응답에 새 전체 블록 비교를 추가하는 접근은 이 비용을 다시 늘리므로 적용하지 않았다.

1440×900, 1240×760과 1440×900의 200% 확대에 해당하는 720×450 CSS viewport를 확인했다. 마지막 조건에서 떠 있는 패널 때문에 CSS grid 자동 배치가 밀려 캔버스가 첫 번째 52px 열로 이동하는 기존 결함을 발견했다. 좌·중앙·우의 열과 행을 명시했고, 좌측/양쪽 패널을 펼쳐도 캔버스 x=52, width=616, height=450이 유지됨을 실측했다. 좁은 화면의 기존 패널이 캔버스를 덮는 동작은 유지되며 패널을 닫으면 전체 캔버스가 다시 보인다. 브라우저 메뉴의 실제 zoom 명령을 실행한 검증과는 구별한다.

QA 원본·비교 미리보기·측정 JSON·프로파일은 `.tmp/responsiveness-final/`에 보존한다. 임시 앱 진입점과 벤치마크 테스트는 소스 트리에서 제거했다. Impeccable의 변경 파일 정적 검사는 진단 0건이며 화면과 행동 검증을 대신하지 않는다.

후속 최종 검증은 `npm run check` 292.14초 통과, 6,984개 테스트 통과·4개 skip이다. 기존 coverage floor, typecheck, lint, build, page artwork parity와 image protocol smoke를 통과했다. 로그는 `.tmp/responsiveness-final/check-confirmed.log`에 보존했다.

이후 사용자 요청에 따라 v2.7.12 커밋 직전에 QA PNG와 갤러리를 정리했다. 위 경로의 측정 JSON과 재현 소스·로그는 유지한다.

사용자 원본과 보관함은 사용하지 않고 격리 데이터로 측정했다. 모델 실행 잠금, 저장 revision 검증, transaction publication, 공개 IPC와 저장 형식은 유지했다. Impeccable optimize 절차로 병목을 확인한 뒤 수정했다.

## 함께 확인한 경로

- 캔버스: 실제 `OverlayBlockLayer`, 20블록으로 확대 30회·이동 preview 30회·한 블록 문구 변경 20회. 확대/이동 중 추가 글자 측정 0회. 문구 변경은 실제 레이아웃을 재계산. 각 구간에서 50ms 이상 long task 0회.
- 페이지 탐색: 30/500페이지의 서로 다른 위치 20회 선택을 실제 Chromium에서 실행. 선택이 노출되고 long task 0회. 탐색 render time은 실행마다 변동해 속도 개선 수치로 제시하지 않는다.
- pan/wheel 입력: 기존 frame 묶음 처리 및 단축키 우선순위 회귀 테스트. 이미 한 프레임으로 묶이는 경로는 변경하지 않았다.
- 블록 편집: 기존 이동 preview의 레이아웃 재사용, resize 대상만 재측정, 저장 중 추가 편집·실패·재시도·페이지 변경 계약 검증.
- 가져오기/내보내기: 기존 이미지 준비는 publish 잠금 밖, 공유 export는 snapshot 읽기 보호 및 artifact retention을 사용함을 확인. 이 보호는 유지했다.
- 보관함: 기존 조회 요청 합치기와 원자적 publication 읽기 경계를 확인. 전체 보관함을 영구 캐시하거나 파일 검증을 생략하지 않았다.
- 이벤트: 일반 job의 IPC 묶음 처리/완료 checkpoint 보존, 관리 작업의 동시 ID별 타이머·취소·실패·완료·동일 ID 재사용을 검증.
- 잠금: 모델 독점과 A 페이지 처리/B 페이지 편집의 활동 자원 경계 및 async owner 보존 회귀 테스트.

검수표의 parsing·최신 데이터 읽기·검증·파일 publication은 여전히 기존 쓰기 경계 안에 있다. 잠금 범위를 추측으로 해제하지 않고 그 안에서 확인된 중복 계산을 줄였다. 모델 추론 속도, GPU 메모리 소비, 실제 사용자의 모든 원고 조합에 대한 성능 완료를 주장하지 않는다.
