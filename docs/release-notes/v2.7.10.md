# v2.7.10 — Inpainting GPU runtime fixes

## NVIDIA CUDA

- Install the missing cuFFT dependency used by LaMa inpainting. This fixes the reported cuFFT loading failure that caused a CUDA worker to exit and fall back to the CPU (#117).
- Repair CUDA caches with missing, empty, or non-file DLLs, and validate both CUDA and cuDNN cache versions before reuse.
- Replace the bundled Windows Koharu runner's `sm_89`-only PTX with an explicit `sm_75` build. This removes the newer-target-only obstacle for RTX 20/30 GPUs and provides forward-JIT PTX for later NVIDIA architectures, subject to driver and library requirements.
- Preload cuFFT before inference and reject incompatible PTX inventories during Windows packaging so the build host's GPU cannot silently narrow the shipped target again.

## AMD ZLUDA

- Verify the pinned ZLUDA archive and six runtime DLLs by exact size and SHA-256 before starting a worker.
- Repair damaged ZLUDA and cuRAND support caches through staged installation and rollback, preserving the previous cache when repair fails.
- Select only the canonical `zluda/<name>` DLLs, preventing diagnostic `trace` copies from overwriting normal runtime libraries.
- Reject empty or non-file DLLs in the native bootstrap as well as the host installer.

## Validation and compatibility

- Add regression coverage for NVIDIA RTX 20/30/40/50, AMD RX 6000/7000/9000, Intel Arc/integrated, no-GPU, and Metal backend selection, plus CUDA/HIP device isolation.
- Validate the real published ZLUDA ZIP, extracted DLL hashes, and damaged-cuFFT cache repair. These installation and routing tests are not hardware certification.
- Intel-only Windows systems retain CPU execution for this Koharu/LaMa path; this release does not add Intel GPU acceleration.
- Actual inference on every NVIDIA generation and AMD GPU has not been certified. CPU fallback must not be counted as GPU validation.

## Distribution and signing

Windows x64 and Apple Silicon macOS packages use the existing verified release workflows. Windows artifacts are unsigned under the current signing configuration. Unless Developer ID and notarization credentials are configured, macOS packages are ad-hoc signed, not Apple-notarized, and may require approval in System Settings → Privacy & Security.
