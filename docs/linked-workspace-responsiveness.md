# 자동 결과 동기화·보관함 초기 로딩·삭제

## 동기화 중 편집

자동 렌더는 짧은 library 읽기 경계에서 페이지를 복제하고 기존 snapshot lease로
이미지 파일 수명을 보존한다. 이후 같은 페이지의 텍스트 저장은 허용한다. 렌더
도중 입력이 발생해도 진행 중인 캡처를 취소하지 않는다. 출력 이미지와 복구 문서는
캡처한 버전을 함께 반영하고, 뒤에 저장된 편집은 다음 동기화 항목으로 유지한다.

출력 경로 쓰기와 화·페이지 구조 읽기 예약은 유지한다. 출력 설정 변경과 삭제는
기존 generation 검증으로 늦은 결과를 거절한다. 모델 실행의 독점 계약은 바꾸지 않는다.
실제 AppActivityGate와 저장 facade를 연결한 테스트로 렌더 도중 같은 페이지 저장을
검증하고, 지연 렌더와 후속 편집이 각각 올바른 버전으로 출력되는지 확인한다.

## 삭제 범위와 실패 복구

작품·화 삭제 확인창에서 직접 지정한 폴더의 생성 파일 삭제도 기본 체크한다.
해제하면 그 폴더의 파일은 보존한다. UI가 표시한 선택을 기존 IPC의 선택적 boolean
인자로 명시적으로 전달하며, 인자 없는 기존 호출의 동작은 유지한다.

기본 결과 폴더에서는 해당 연결이 기록한 생성 파일과 복구용 원본 복사본을 삭제한다.
앱 밖의 원본, 기록된 해시와 다른 파일, 다른 화가 참조하는 파일은 보존한다.
사용자가 지정한 폴더 자체는 삭제하지 않는다. 기본 결과 폴더는 비어 있을 때만
비재귀 rmdir로 정리한다. 정션·심볼릭 링크 경로는 삭제 전에 거절한다.

진행 중인 출력 위치 변경을 기다리고, 삭제 대상의 새 동기화를 차단한 후 기존
렌더를 취소·종료한다. 삭제 파일을 journal과 함께 같은 경로에 임시 이동하고
해시를 다시 검증한 뒤 보관함 삭제를 수행한다. 보관함 삭제 전 실패는 파일을
복원하고, 이후 중단은 다음 시작 시 실제 보관함 존재 여부를 확인해 마무리한다.
복구 실패는 오류로 전달하며, 충돌 파일을 덮어쓰지 않는다.

새 삭제 모듈의 최초 Windows 전체 테스트 측정은
`.tmp/report-fixes-coverage-windows.json`에 보존한다. SHA-256은
`98e661f71ffdf69b490f74c1f79473d3162ae08848824584a33135e615145f66`이다.
line 94.44%, statement 91.01%, function 100%, branch 80.39%를 새 보호 기준으로
등록했다. 이 실행에서 기능 테스트 7,001개는 통과했고, 당시 등록 누락을 지적한
커버리지 목록 테스트 1개는 실패했다. `useConfirmDialog`의 기존 보호 기준은
원래 Node 22 baseline의 100%를 그대로 등록했다. 기존 artifact와 다른 파일의
보호 기준은 변경하지 않는다.

## 확인창 검증

공통 ConfirmModal의 중복 내부 테두리와 경고 장식을 제거하고 기존 Modal·CheckboxField·
action primitive를 사용한다. raw chrome 색상은 추가하지 않았으며 기존 CSS의
색상 리터럴 부채는 27개에서 20개로 줄었다. 실제 삭제 hook으로 확인창을 열어
1440×900 및 1240×760의 200% 확대 상태에서 기본 체크·줄바꿈·버튼 노출을 확인했다.
최종 문구 정리 후에도 같은 크기로 다시 캡처해 확인했다. 캡처 이미지는 사용자
지침에 따라 커밋 직전에 정리하며, 실행 로그는 `.tmp/report-fixes-qa-copy-wide.log`와
`.tmp/report-fixes-qa-copy-narrow.log`에 남긴다.

최종 `npm run check`는 26개 단계를 모두 통과했다. 824개 테스트 파일에서
7,002개 테스트가 통과했고 기존 4개는 skipped였다. 커버리지 보호 검사, 실제 build,
페이지 출력 픽셀 parity와 이미지 프로토콜 smoke도 포함한다. 실행 로그는
`.tmp/report-fixes-check-accepted.log`다. 변경한 확인창·스타일·삭제 hook에 대한
Impeccable 정적 detect 결과는 `[]`이며, 정적 검사 결과와 별개로 위 실제 캡처를
직접 확인했다. 장시간 모델 작업과 릴리즈 조작은 실행하지 않았다.

2026-09-21 삭제 확인창의 파일 보존 부연 문장만 모든 언어에서 제거했다.
삭제 정책과 체크 기본값은 유지한다. 문구 변경 후 확인창·번역 카탈로그 테스트
9개와 `npm run build`를 다시 통과했다.

## 자동 저장 실패 기록 복구 (2026-09-21)

실사용 대기열에서 현재 페이지와 발행 revision이 모두 일치하고 결과 파일의
크기·SHA-256도 발행 기록과 일치하는데, 이전 revision의 terminal failure가 남은
항목을 확인했다. 시작 시 최신 출력이 확인되어도 기존 실패 항목을 삭제하지 않고,
이미 대기열에 있다는 이유로 이전 revision을 교체하지 않던 경로가 원인이다.
당시 최초 실패의 상세 오류는 로그에 기록되지 않아 확정하지 않았다.

이제 시작 시 최신 결과가 이미 있으면 완료된 대기 항목을 제거하고, 미발행된
새 revision이 있으면 그 revision으로 교체한다. 같은 revision의 실제 오류는
재시도 한도를 유지한다. 보관함에 더 이상 없는 화의 연결과 대기열은 해제하되
그 폴더의 파일은 삭제하지 않는다. 파일 접근·파싱 오류를 보관함 삭제로 취급하지 않는다.

캡처 준비 중 revision이 바뀌면 새 버전을 대기열에 반영하며 저장 실패로 세지 않는다.
캡처를 마친 뒤의 편집은 기존 사본 렌더와 독립적으로 다음 저장에 남긴다.
실제 실패는 기존 오류 보고 경로에 화·페이지 ID, 시도 횟수, 원본 오류를 남긴다.
`linkedWorkspaceQueueRecovery.test.ts`의 6개 시나리오와 기존 동기화 테스트로
완료 기록 복구, 미발행 수정 보존, 캡처 전 변경, 실제 실패 보존, 삭제된 화의
출력 파일 보존을 검증한다. 복구 문서만 있고 첫 결과 이미지가 아직 발행되지
않은 실패 항목은 완료 처리하지 않는 것도 별도로 확인한다.
