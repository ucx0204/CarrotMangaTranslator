# Hayai 페이지 작업 (#121)

- Hayai는 `hayaiTranslationUi` 설정으로 기존 `LegacyTranslationOptionsModal`과 새 `PageWorkflowModal`을 선택한다. 기본값은 새 화면이며 Paddle은 기존 경로를 유지한다.
- 공개 IPC는 `preflightPageWorkflow`, `startPageWorkflow`, `getPageWorkflowRun`이다.
- `pageWorkflowService`가 단계 순서·페이지 소유권·취소·저장을 조율한다. 단계 어댑터는 기존 OCR, 번역, C23 폰트 분석, 제거, 배치 구현을 호출한다.
- 번역은 저장된 원문을 고정 영역 입력으로 전달한다. 검출과 OCR은 번역 엔드포인트를 시작하지 않는다.
- 원문/번역문/서식은 기본적으로 빈 항목만 채운다. 일괄 편집은 사용자가 지정한 변경 명령이며, 규칙 내용은 실행 시작 시 고정된다.
- 번역 성공 여부는 기존 고정 블록 파이프라인의 판정을 따른다. 일부 블록의 미출력·필터 제외만으로 페이지 실패나 강제 재시도를 추가하지 않는다. 정상 번역은 저장하고 응답이 없는 블록은 기존 값을 유지한다. 빈 번역은 선택한 자동 검수 단계에서 확인 대상으로 남긴다. 모델 요청·파싱 등 실제 실패는 실패 기록과 페이지 오류로 표시한다.
- 번역 실패 이후에도 독립적인 원문 제거는 실행한다. 공통 런타임 오류와 저장 충돌은 실행을 중단한다.

## 페이지 작업 UI

- 헤더의 기존/새 버전 선택을 UI 설정에 저장한다. 전환 직전 실제 너비에서 다음 너비로 280ms 보간하며, 연속 전환은 현재 너비에서 이어진다. 동작 줄이기 설정에서는 공간 이동을 생략한다.

- 모달은 화면 높이를 채우고 실행 순서는 420px을 사용한다. 나머지 폭은 대상 페이지에 배정하며 썸네일은 기존 번역 설정과 같은 컴포넌트·크기를 사용한다.
- 각 작업과 하위 옵션의 설명은 툴팁으로 제공한다. 드롭다운을 열면 툴팁을 닫아 선택 항목을 가리지 않는다.
- 프리셋 편집은 선택한 이름을 유지하고 수정 표시를 붙인다. `변경 저장`은 기존 ID와 이름을 유지하며, `새로 저장`은 별도 프리셋을 만든다.
- 프리셋은 즐겨찾기 우선으로 정렬한다. 사용자 프리셋은 삭제 확인 후 제거하고 즐겨찾기 참조도 함께 정리한다. 설정은 `pageWorkflowFavoritePresetIds`에 저장한다.
- 옵션 재검사 중에는 마지막 요약을 유지하고 시작 버튼을 잠근다. 결과를 확정할 때 요약을 교체해 체크마다 숫자와 목록이 깜빡이지 않게 한다.

## 저장과 재개

`dataRoot/page-workflows/<runId>.json`에 계획·선택 대상·고정 규칙을 저장한다. 페이지의 선택적 `pageWorkflow`에 단계별 입력/출력 지문과 완료 기록을 저장한다. 콘텐츠와 완료 기록, 번역의 누적 기억·용어집은 같은 보관함 트랜잭션에서 확정한다.

같은 실행의 재개는 저장된 계획과 규칙을 사용한다. 새 실행은 새 규칙 스냅샷을 만든다. 설정 지문에는 인증 정보를 저장하지 않는다. 번역문 수정은 원문 제거 완료 기록을 무효화하지 않는다.

새 준비 블록의 `textDisplayMode: translation-only`는 빈 번역문을 화면·PNG·PSD에 그리지 않는다. 기존 블록의 원문 대체 표시는 유지한다. `workflowOrigin`은 최초 서식과 OCR 기하를 보관하며, 수동 변경과 자동 적용을 구별한다.

## 검증 범위

### 페이지 간 런타임 재사용 (#129)

- 한 챕터의 OCR 단계는 Hayai Python 워커와 모델을 한 번 준비하고 페이지별 요청을 순서대로 보낸다. 기존 `process_page`와 OCR 결과 정규화를 그대로 사용하며, 한 페이지를 저장한 뒤 다음 페이지를 요청한다. 입력 전체를 미리 OCR하는 방식이 아니므로 중간 취소·페이지 실패에도 앞선 완료 결과는 유지된다.
- 번역 단계는 기존 endpoint session을 한 번 생성하고 각 페이지 파이프라인이 빌려 쓴다. 번역 입력, 누적 기억과 용어집은 페이지마다 최신 저장 상태에서 다시 읽는다. 단계 종료·취소·실패 시 기존 프로세스 종료 계약으로 정리하고, 종료 실패 시 다음 모델을 시작하지 않는다. 페이지별 복구 가능한 실패 후에는 새 session으로 남은 페이지를 처리한다.
- 제거 전 말풍선 검출과 최종 배치는 같은 job 소유 runner의 원본 검출 결과를 공유한다. 원본 경로·크기·수정/생성 메타데이터를 키로 사용하고, 최대 128항목/64MiB까지만 보관한다. 초과 결과는 재검출하며 배치 좌표·여백·번역문 처리는 매번 현재 페이지로 계산한다.
- 재개할 때 모든 선택 페이지가 이미 완료한 단계는 준비를 생략한다. 일부 페이지만 완료한 폰트 단계는 전체 선택을 준비하고 기존 완료 페이지의 연속성 복원 절차를 유지한다.
- CPU OCR의 낮은 프로세스 우선순위, 모델 다운로드 진행 처리, 요청 timeout과 취소에 따른 프로세스 트리 종료를 기존 구현에서 재사용한다. 모델 상주 범위는 챕터 내 단계이며 전역 캐시를 추가하지 않는다.

`pageWorkflowSessions`는 실제 페이지 번역 파이프라인의 3페이지/1 endpoint 시작과 OCR 저장·실패·취소 순서를 검증한다. `hayaiRecognitionSession`은 설치/모델 경계만 대체하고 실제 JSON-lines 프로세스 통신과 기존 CJS 정규화를 사용한다. Python `test_hayai_paths.py`는 동일한 `process_page` 입력으로 단일 실행/워커 결과의 일치를 확인한다. 이는 생명주기와 결과 계약 검증이며 GPU 실측 배속을 뜻하지 않는다.

2026-09-27 RTX 4090/CUDA 12.6의 실제 Hayai 모델 스모크: 합성 일본어 원고 3장의 단일 프로세스별 실행 합계 30.347초, 워커 공유 실행은 종료 포함 15.347초였다. 워커 첫 요청 13.818초, 후속 요청 0.224/0.227초, 모델 로드 1회이며 6개 출력 JSON이 모두 일치했다. 전체 테스트가 동시에 실행된 작은 샘플이므로 실원고 전체 처리의 배속으로 일반화하지 않는다. 입력·출력·로그·측정 결과는 `.tmp/workflow-reuse-smoke-u1W8iz/summary.json`과 같은 디렉터리에 보존한다.

새 session 두 파일의 최초 커버리지 기준은 `.tmp/workflow-session-coverage/coverage-summary.json`의 실측값이다(SHA-256 `5ebfab187773f8d905b0077289ee15f16e2f44287346ed02311ad496adb76598`). 기존 파일 기준과 역사 provenance는 변경하지 않는다.

- `pageWorkflowService`, `pageWorkflowAdapters`, `pageWorkflowPersistence`, `pageWorkflowRunStore`, `pageWorkflowRuleRenderer`, `pageWorkflowModal` 테스트.
- 실제 파일 트랜잭션의 중간 종료/복구, 규칙 중복 적용 방지, 저장 충돌, 렌더러 글자 크기 계측, 기존 고정 블록 OCR 기하와 래스터 크기 결과 비교.
- 기존 Paddle 모달, 캔버스, PSD, 내보내기 취소 회귀 테스트.
- 프로덕션 컴포넌트 UI 캡처: 1600×980, 1240×760, 200% 확대, 읽기 24px, 긴 원문, 규칙 오류.

네이티브 모델을 모두 구동하는 실제 만화 전체 처리의 픽셀 단위 비교는 별도 검증 대상이다. 기존 알고리즘과 모델 artifact를 재사용한다.

## 2026-11-03 작업 센터와 저장 결과 동기화

- 실행 순서는 선택된 화 → 선택된 단계 → 해당 화의 페이지 순서다. 진행 이벤트는 실제 화 ID와 제목을 담고, 단계 준비 전에 표시 문맥을 교체한다. 제거 준비 메시지에 직전 자동 서식의 페이지 이름이 남지 않는다.
- 바깥 runner만 저장 완료 또는 이미 완료된 페이지의 건너뛰기 이후 `page_done` 체크포인트를 보낸다. 전체 실행은 계속 `running`이며, 단계 작업 수는 체크포인트에서 증가한다. 저장 실패에는 체크포인트를 보내지 않는다.
- renderer는 이 체크포인트에서 현재 화를 기존 dirty-page merge로 갱신하고, 보관함 요약도 갱신한다. 다른 화의 이벤트는 현재 편집창을 다시 읽지 않는다. 보관함 읽기는 기존 MCP metadata 갱신의 coalescing coordinator를 공유하여 중복 요청과 오래된 응답의 덮어쓰기를 막는다.
- 새 완료 기록에는 선택한 `stages`를 저장한다. 번역 후 제거·배치·검수가 남아 있으면 전체 페이지/화 완료로 판정하지 않는다. 빈 페이지도 번역 단계를 성공적으로 통과한 경우 완료되며, OCR·검수만 실행한 빈 페이지는 번역 완료가 아니다.
- 과거 `translate: empty` 기록과 빈 블록을 가진 `idle` 페이지는 공통 완료 판정과 보관함 요약에서 읽기 호환한다. 원본·출력 이미지나 사용자 파일을 재작성하거나 재번역하지 않는다.
- 회귀 검증: `pageWorkflowProgress`, `pageWorkflowService`, `pageWorkflowPersistence`, `pageWorkflowEmptyCompletion`, `workflowLiveRefresh`, `mcpLibrarySynchronization`. 실제 `LibraryTree`/`StatusPopover`의 1440×1000 및 780×1000 QA 캡처로 상태·긴 작업 문구·잘림·겹침을 확인했다.
