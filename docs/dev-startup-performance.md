# 개발 실행과 앱 시작 성능 (2026-11-08)

`npm run dev`는 개발용 Electron 부트스트랩 번들과 파일별 SHA-256 캐시를 사용한다.
일반 `build`/`compile:electron`은 기존 개별 모듈 출력과 실제 바이트 검증을 유지한다.
개발 번들 여부가 컴파일 캐시 식별자에 포함되므로 배포 빌드가 개발 출력을 재사용하지 않는다.

## 확인한 병목과 변경

- 시작 전 캐시 판정이 약 1 GB의 런타임 입력/출력과 수천 개의 코드 파일을 매번 읽었다.
  개발 실행에서만 size, inode, device, mtime/ctime/birthtime 나노초가 같은 파일의
  SHA-256을 재사용한다. 파일 추가/삭제, 출력 손상, 빌드 중 입력 변경은 재검증한다.
  배포 검증에는 이 메타데이터 최적화를 적용하지 않는다. 경로 정렬 중의 중복 경로 계산과
  제외된 모델 디렉터리 순회도 제거했다.
- Electron 시작 시 앱 모듈 약 1,587개를 개별적으로 로드했다. 개발 컴파일의 마지막에
  Vite SSR CommonJS 번들을 만들되 패키지/네이티브 모듈은 외부 의존성으로 남긴다.
  모듈별 `__dirname`, `__filename`, `require.resolve`는 기존 출력 위치를 유지한다.
  워커 파일은 계속 별도로 출력하며 실제 worker_threads 실행과 초기화 순서/공유 상태의
  번들 전후 동등성을 테스트한다. 별도 로더나 Node 내부 API 패치는 사용하지 않는다.
- 메인 모듈 로딩 후에는 연결된 결과 폴더 초기화가 대부분의 시간을 차지했다.
  트랜잭션/이동/삭제 복구와 임시 파일 정리는 그대로 수행한다. 이후 유휴 연결만
  `cache/linked-workspace-startup-v1.json`의 이전 감사 결과를 재사용한다.
  연결 레코드, 화 JSON, 원본과 복구용 원본, 출력·마스크·인페인트 자산과 그 원본,
  복구 미러의 파일 식별자를 모두 확인한다. 상위 디렉터리의 교체/정션도 확인한다.
  대기 큐, 오류, 미완성 옛 레코드, 누락/변경 파일은 원래 전체 감사로 돌아간다.
  감사 전후 증거가 같고 대기 큐가 비어 있을 때만 기록한다. 캐시는 원본 데이터가 아니며
  없어지거나 손상되거나 저장에 실패해도 전체 감사로 복구된다.
  컴파일된 캐시 모듈의 파일 식별자도 포함하므로 재빌드/설치 후에는 다시 감사한다.

## 측정과 범위

Windows의 동일 PC에서 관찰한 값이며 디스크 캐시 상태에 따라 달라진다.

| 구간                   | 변경 전 |   변경 후 |
| ---------------------- | ------: | --------: |
| 런타임 자산 캐시 판정  |  7.87초 | 약 0.10초 |
| 격리 앱 메인 모듈 로딩 | 19.64초 |    0.80초 |
| 격리 앱 화면 로드      | 21.31초 |    2.59초 |

기존 실제 앱의 `bootstrap:start`→`loaded-main`은 44.37초였다.
번들 적용 후 실제 사용자 데이터로 계측한 연결 초기화는 15.336초였다.
보관함 화 JSON은 233개/약 778 MiB, 연결 레코드는 99개였다.
새 캐시의 **파일 변경 검사만** 읽기 전용으로 측정하면 99개 모두 1.066초였다.
이 값은 실제 보관함 전체 시작 시간과 동일하지 않다. 전체 보관함 목록 읽기와 처음
감사하는 비용은 남아 있으며, 최초 실행/재빌드 이후에는 전체 감사로 캐시를 채운다.

측정 산출물은 `.tmp/startup-profile/`의 `before/profile.log`,
`after/profile.log`, `metadata-validation.json`, `build-cache-timings.json`이다.
격리 실행은 실제 production main/preload와 개발 렌더러를 사용하고 데이터 루트만 분리했다.
사용자 원본·보관함·출력물은 성능 검증의 정리 대상으로 사용하지 않는다.

최종 개발 캐시 준비 후 두 단계가 모두 실제 skip인 반복 측정은 런타임 141 ms,
Electron 1,442 ms(합계 1.583초)였다. 준비 직전 배포 빌드가 출력을 바꿨으므로
첫 회에는 런타임 2.233초와 Electron 재컴파일/번들 11.513초가 들었다.

## 검증 및 되돌리기

빌드 캐시/번들, 기존 연결 복구·삭제·이동, 시작 잠금 및 유지보수 테스트를 실행한다.
같은 크기의 수정 및 mtime 복원, 삭제된 출력, 손상된 캐시, 감사 중 변경,
남아 있는 큐, 정션 치환을 회귀 테스트한다. 타입 검사, lint, 개발/배포 빌드 및
격리된 실제 Electron 시작과 렌더러 IPC 연결을 확인한다.

최종 관련 12개 테스트 파일/148개 테스트, TypeScript/JS 타입 검사, 전체 lint,
유지보수·스크립트 진입점·오류 처리 규칙, 개발 컴파일 및 배포 빌드가 통과했다.
전체 아키텍처 검사에는 작업 시작 때부터 변경 중이던 `ipcSettingsSchemas.ts`의
runtimeImports 15/허용 14 위반이 남아 있다. 이 작업의 두 직접 소비 증가는 위 근거에
따라 기록했고, 별도 설정 작업의 코드는 수정하지 않았다.

새 모듈의 coverage 출처는 `.tmp/dev-startup-coverage/coverage-summary.json`이며 SHA-256은
`ce767c21c9c5bf6582329db89d1053380e62619219bf5d0348c8829f54a381b3`이다.
기존 coverage 기준은 낮추지 않고 새 모듈의 최초 실측만 inventory에 추가했다.
storage의 직접 소비자 상한 43→44, libraryPaths의 상한 32→33은 기존 저장/경로 권위의
직접 재사용에 따른 실측 증가다. 전역 기준은 변경하지 않는다.

개발 번들을 끄려면 dev의 `--dev-bundle` 및 cache step의 `devBundle` 옵션을 함께 끈다.
해시 재사용은 dev cache step의 `reuseFileDigests` 옵션으로 제어한다.
연결 감사 캐시는 composition에서 `startupCache` 주입을 제거하면 전체 감사로 돌아간다.
어느 경우에도 원본·출력 파일이나 연결 레코드를 삭제할 필요가 없다.

Vite 번들은 [Rolldown의 Node 플랫폼](https://rolldown.rs/reference/InputOptions.platform)과
[외부 모듈 계약](https://rolldown.rs/in-depth/external-modules)을 따른다.
